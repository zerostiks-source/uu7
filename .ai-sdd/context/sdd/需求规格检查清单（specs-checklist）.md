# 需求规格检查清单（Specs Checklist）

> 用途：specs 生成后，逐项检查确保规格描述完整且可验证。

---

## 一、能力拆分与独立性

| # | 检查项 | 依据 |
|---|--------|------|
| 1.1 | 每个 spec 对应一个独立能力，按系统或模块拆分 | config.yaml specs rules |
| 1.2 | spec 之间无循环依赖，各自可独立验证 | — |
| 1.3 | proposal 中列出的每个 capability 都有对应的 spec 文件 | — |
| 1.4 | 未遗漏 proposal 中隐含但未显式列出的能力 | — |

## 二、行为描述质量

| # | 检查项 | 依据 |
|---|--------|------|
| 2.1 | 只描述系统应具备的行为（What），不写代码实现细节（How） | config.yaml specs rules |
| 2.2 | 行为描述使用可验证的语言（"系统应…"而非"可能需要…"） | — |
| 2.3 | 主流程行为描述完整，有明确的输入和输出 | — |
| 2.4 | 未包含架构选型、技术方案等 design 阶段内容 | — |

## 三、业务术语与规则引用

| # | 检查项 | 依据 |
|---|--------|------|
| 3.1 | 引用既有业务规则与术语，未自行发明业务概念 | config.yaml specs rules |
| 3.2 | 使用的术语与 domain-glossary 一致 | domain-glossary |
| 3.3 | 涉及的业务规则引用了 business-rules 中的已有规则 | business-rules |

## 四、例外场景覆盖

| # | 检查项 | 依据 |
|---|--------|------|
| 4.1 | 例外场景在 specs 中有对应行为要求 | config.yaml specs rules |
| 4.2 | 边界条件已明确（空值、超限、并发、权限不足等） | edge-cases |
| 4.3 | 异常路径有明确的系统响应描述 | — |

## 五、与 proposal 一致性

| # | 检查项 | 依据 |
|---|--------|------|
| 5.1 | specs 覆盖范围与 proposal 的 In Scope 一致，未越界 | — |
| 5.2 | proposal 中的验收标准在 specs 中有对应行为体现 | — |
| 5.3 | proposal 中的待确认项在 specs 中已标注处理方式（已确认/仍待确认/假设） | — |

## 六、待确认项

| # | 检查项 | 依据 |
|---|--------|------|
| 6.1 | 存在歧义的行为要求已标注 "TODO: 待确认" | config.yaml context |
| 6.2 | 未确认的业务规则优先级、数据归属等已显式列出 | config.yaml context |
