# 需求提案检查清单（Proposal Checklist）

> 用途：proposal.md 生成后，逐项检查确保提案完整性与可评审性。

---

## 一、业务目标与动机

| # | 检查项 | 依据 |
|---|--------|------|
| 1.1 | 明确说明"为什么要做这个变更"，有业务背景或用户痛点描述 | — |
| 1.2 | 业务目标与 business-goals 中的项目范围一致，未超出边界 | business-goals |
| 1.3 | 变更类型明确（新增功能 / 修改现有流程 / 缺陷修复 / 优化） | — |

## 二、范围与边界

| # | 检查项 | 依据 |
|---|--------|------|
| 2.1 | 明确列出"包含什么"（In Scope） | — |
| 2.2 | 明确列出"不包含什么"（Out of Scope / 排除项） | — |
| 2.3 | 涉及的系统/模块已明确标注，与 system-structure-capability 一致 | system-structure-capability |
| 2.4 | 未擅自假设新的系统边界、主数据归属或接口能力 | config.yaml context |

## 三、AS-IS / TO-BE 差异

| # | 检查项 | 依据 |
|---|--------|------|
| 3.1 | 涉及现有流程时，已描述当前行为（AS-IS） | config.yaml proposal rules |
| 3.2 | 已描述变更后的目标行为（TO-BE） | config.yaml proposal rules |
| 3.3 | AS-IS 与 TO-BE 的差异点清晰可比 | — |

## 四、能力拆分

| # | 检查项 | 依据 |
|---|--------|------|
| 4.1 | Capabilities 部分列出了所有需要的独立能力 | — |
| 4.2 | 每个 capability 可独立对应一个 spec 文件 | config.yaml specs rules |
| 4.3 | 复用已有能力优先于新增能力 | config.yaml context |

## 五、影响分析

| # | 检查项 | 依据 |
|---|--------|------|
| 5.1 | 已识别受影响的现有功能/接口/数据 | — |
| 5.2 | 已评估对上下游系统的影响 | integration-map |
| 5.3 | 数据归属与主数据源已确认或标注待确认 | data-ownership |

## 六、验收标准

| # | 检查项 | 依据 |
|---|--------|------|
| 6.1 | 有可验证的验收标准（非模糊描述如"用户体验好"） | — |
| 6.2 | 验收标准覆盖主流程和关键异常场景 | — |

## 七、待确认项与风险

| # | 检查项 | 依据 |
|---|--------|------|
| 7.1 | 信息不足的关键项已显式列为"待确认问题" | config.yaml proposal rules |
| 7.2 | 未确认的数据归属、规则优先级、接口能力等已列出 | config.yaml context |
| 7.3 | 已知风险和假设前提已记录 | — |
